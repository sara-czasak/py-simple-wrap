    Contributing to py-simple-wrap 🚀

    First of all, thank you for being here! I created py-simple-wrap to help others on their learning journey, and I'm excited to have you join me.

    I struggle with anxiety myself, so I totally understand if you're feeling nervous about contributing. Please don't be! The absolute worst thing that could happen is that I might ask for a few changes before merging your code. This is a safe space to learn, make mistakes, and grow together.

    📚 New here? The Contributor Hub has copy-paste templates for docstrings and tutorial pages, so you're not guessing at formatting on your first PR.

    ⭐ Enjoying the project?

    If py-simple-wrap has been useful, or you just like what it's doing, a star means a lot — it helps other beginners discover the project and keeps me motivated to keep building it. It takes two seconds and costs nothing. 🙏

    The "Simple" Philosophy

    Before submitting a new feature, ask yourself: "Does this make a complex task easier for a beginner?" My goal is to keep things intuitive and easy to read.

    📂 Understanding the Project Structure

    Before making your first contribution, here's a quick overview of where everything lives.

    py-simple-wrap/
├── py_simple_package/
│   └── src/
│       └── py_simple/       # Python package source code
├── tests/                   # Automated tests
├── docs/                    # Documentation and tutorials
├── module-book/             # Module reference website
├── landing/                 # Website landing page
├── .github/                 # GitHub workflows and templates
├── scripts/                 # Project maintenance scripts
├── pyproject.toml           # Package configuration and dependencies
├── CONTRIBUTING.md          # Contribution guidelines
└── README.md                # Project overview

    Where should I make changes?

    Adding or updating a helper?

    Look inside py_simple_package/src/py_simple/. This is where the Python source code lives.

    Adding tests?

    Look inside tests/. Tests verify that helpers work correctly and help prevent bugs.

    Improving documentation?

    Start with docs/ or the relevant Markdown files in the repository. The module-book/ directory contains the module reference website.

    Why is the Python package inside src/?

    The project uses a source-based layout to separate the Python code from the rest of the repository.

    The package is located at:

    py_simple_package/src/py_simple/

    But when you install py-simple-wrap, you import it using:

    from py_simple import make_blank_file

    You don't need to include the repository's directory structure in your imports.

    What's an editable installation?

    When contributing, you want to test changes to your local code without reinstalling the package every time.

    An editable installation, such as:

    pip install -e .

    connects your Python environment to the source code in your cloned repository. Changes you make to Python files can then be tested directly.

    A normal installation, such as:

    pip install py-simple-wrap

    installs the published package instead.

    Tip: If you're contributing, follow the environment setup instructions below rather than installing the published package.

    🛠️ Step-by-Step Guide for Beginners

    If you've never contributed to an open-source project before, here is exactly how to do it:

    1. Fork the Project: Click the "Fork" button at the top right of this GitHub page. This creates your own copy of the project.
    2. Get the Clone Link:
    3. On your fork's GitHub page, click the green <> Code button.
    4. Make sure the HTTPS tab is selected.
    5. Click the little "copy" icon (two overlapping squares) next to the URL to copy it to your clipboard.
    6. Clone Your Fork: Open your terminal, type git clone, and then paste the link you just copied:
    git clone https://github.com/YOUR_USERNAME/py-simple-wrap.git
    1. Create a Branch: It's best to do your work on a new branch:
    git checkout -b my-new-feature
    1. Set up the Environment: We recommend using uv for lightning-fast dependency management, but standard pip works too!
    2. Using uv (Recommended):
      • Install uv if you haven't already: Installation Guide
      • Sync the project dependencies: 
        uv sync --all-extras --dev
      • Run the tests to make sure everything works: 
        uv run pytest

    3. Using pip:

      • Create a virtual environment and install the package with every extra — the test suite covers every module, including the ones that need extra packages (pygame, matplotlib, Pillow, and so on), so [all] is needed to run it in full: 
        python -m venv .venv
# Activate the virtual environment
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -e .[all,test,docs]
      • Run the tests: 
        pytest

    4. Preview the Docs Locally: If you are modifying documentation or adding new tutorials, you can preview the site locally using MkDocs.

    5. Using uv: 
      uv run mkdocs serve

    6. Using pip: 

      mkdocs serve
      Open http://127.0.0.1:8000 in your browser to view the site.

    7. Write Your Code: Add your awesome new function or fix that bug! If you're not sure how to format a docstring or write a tutorial page, check the Contributor Hub on the docs site — it has copy-paste templates for both, built from this project's actual conventions.

    8. Commit Your Changes: Save your progress with a helpful message:

    git add .
git commit -m "Added a new helper for list cleaning"
    1. Push to GitHub: Send your changes back to your fork:
    git push origin my-new-feature
    1. Open a Pull Request: Go to the original py-simple-wrap repository on GitHub, and you'll see a button that says "Compare & pull request." Click it and tell me a bit about what you did!

    💡 What should I contribute?

    • Report Bugs: If something isn't working, open an "Issue" and let me know.
    • New Ideas: Want to add a "Simple" module for math, strings, or colors? Open an Issue and we can brainstorm it together!
    • Documentation: Spot a typo in this README? I'd love for you to fix it!

    Coding Style

    I try to keep the code "Clean" and "Explicit."

    • Use descriptive function names (like is_file_there instead of check).
    • Always include Docstrings with an example — see the Docstring Template in the Contributor Hub for the exact shape we use.
    • Use existing helper functions (like is_valid_extension) to keep things consistent.

    Thank you for being brave enough to try! I can't wait to see what you build. 🌈✨
